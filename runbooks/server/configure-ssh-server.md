# Конфигурация SSH сервера

**Назначение:** базовая настройка и дальнейшее сопровождение OpenSSH Server  
**Основной каталог конфигурации:** `/etc/ssh/sshd_config.d/`  
**Основной профиль:** `/etc/ssh/sshd_config.d/00-ssh-hardening.conf`  
**Проверено по документации:** 22 ноября 2026 года

## Назначение и границы профиля

SSH — это не просто способ открыть удалённый терминал. Для Linux-сервера он становится основным каналом администрирования, а значит, одновременно является частью плоскости управления инфраструктурой. Через него выполняют команды, передают файлы, создают туннели, подключают IDE, организуют доступ к внутренним сервисам и иногда строят целые bastion-схемы. Поэтому конфигурацию SSH следует рассматривать не как набор случайных параметров безопасности, а как описание того, какие действия сервер разрешает удалённому пользователю после установления соединения.

Базовая политика этого ранбука исходит из достаточно строгой модели:

- сервером управляют именованные пользовательские учётные записи;
- административные права получают через `sudo`;
- аутентификация выполняется по публичным ключам;
- прямой вход под `root` запрещён;
- стандартные механизмы туннелирования выключены;
- SFTP остаётся доступным;
- дополнительные возможности включаются только под конкретную роль и для конкретной группы пользователей.

Это **эталонный исходный профиль**, а не универсальная конфигурация для любой SSH-инфраструктуры. Он подходит как отправная точка для обычного Linux-сервера, на котором администраторам нужны shell-доступ и SFTP, но не нужны произвольные SSH-туннели. Jump Host, удалённая IDE, SFTP-only учётные записи и другие роли описываются отдельными расширениями.

## Принцип организации конфигурации

Главное правило при настройке SSH: **локальную политику SSH следует хранить в `/etc/ssh/sshd_config.d/`, а не редактировать основной `/etc/ssh/sshd_config`**. Основной файл следует воспринимать как точку входа и место подключения дополнительных фрагментов. В нём остаётся конфигурация, поставляемая дистрибутивом, а собственные решения администратора размещаются в отдельных файлах каталога `.d`. Такая организация отделяет настройки операционной системы от локальной политики, упрощает аудит изменений и снижает вероятность того, что обновление пакета затрёт административные настройки.

Сначала необходимо убедиться, что основной файл действительно подключает каталог фрагментов:

```bash
sudo grep -nE '^[[:space:]]*Include[[:space:]]+/etc/ssh/sshd_config.d/\*\.conf' /etc/ssh/sshd_config
```

Ожидаемая директива выглядит так:

```text
Include /etc/ssh/sshd_config.d/*.conf
```

Она должна располагаться до тех директив, значения которых предполагается задавать в `.d`. Если Include отсутствует, каталог не будет применяться только потому, что он существует. В таком случае потребуется один раз подключить его в основном файле. Это единственное исключение, когда потребуется изменить исходный файл: после подключения `Include` все собственные настройки по-прежнему хранятся в `.d`.

### Порядок чтения файлов

OpenSSH раскрывает шаблон `*.conf` в лексикографическом порядке. При этом для большинства параметров действует правило **first obtained value**: используется первое найденное значение директивы, а не последнее. Именно поэтому файл с именем `99-hardened.conf` часто не переопределяет параметры, уже заданные в `50-cloud-init.conf` или другом более раннем фрагменте. Для настройки сервера SSH рекомендуется следующая файловая структура:

```txt
/etc/ssh/
├── sshd_config
└── sshd_config.d/
    ├── 00-ssh-hardening.conf
    ├── 20-ssh-source-penalties.conf   # необязательное расширение OpenSSH 9.8+
    ├── 30-allow-users.conf            # ограничение круга пользователей
    ├── 40-ssh-role-jump.conf          # если сервер выполняет роль Jump Host
    ├── 41-ssh-role-code-server.conf   # если разрешён доступ к code-server
    └── 50-ssh-role-sftp-only.conf     # если есть SFTP-only пользователи
```

Перед созданием файлов необходимо посмотреть, что уже существует:

```bash
sudo find /etc/ssh/sshd_config.d -maxdepth 1 -type f -name '*.conf' -printf '%f\n' | sort
```

Не следует механически переименовывать все файлы дистрибутива или cloud-init. Сначала нужно понять, какие параметры они задают и зачем. Локальный основной профиль должен стоять раньше фрагментов, значения которых он намеренно переопределяет. Если в каталоге уже есть файл, сортирующийся раньше `00-ssh-hardening.conf`, нужно разрешить конфликт осознанно: подобрать ещё более раннее имя либо изменить структуру существующих локальных фрагментов.

Есть и второе следствие правила first-match: бессмысленно добавлять в самый конец ещё один файл с тем же глобальным параметром и ожидать, что он заменит значение из `00-ssh-hardening.conf`. Для ролевых исключений OpenSSH предоставляет блоки `Match`. Они позволяют изменить поддерживаемые параметры для определённого пользователя, группы, адреса или другого условия. Такие исключения нужно проектировать явно и проверять через `sshd -T -C`.

**Практическое соглашение:** одна директива должна иметь одно понятное место управления. Не нужно одновременно задавать `AllowTcpForwarding` в трёх глобальных файлах и пытаться запомнить, какое значение победит.

Также стоит знать о **уникальных подсистемах**. Не дублируйте в drop-in-файлах директивы `Subsystem`, уже объявленные дистрибутивом в основном `/etc/ssh/sshd_config`. В отличие от большинства параметров SSH, повторное объявление подсистемы с тем же именем приводит к ошибке разбора конфигурации. Например, если SFTP уже зарегистрирован дистрибутивом, не добавляйте вторую директиву `Subsystem sftp internal-sftp`.

## Базовый профиль

Создаётся файл: `/etc/ssh/sshd_config.d/00-ssh-hardening.conf` со следующим содержимым:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
AuthenticationMethods publickey

PermitRootLogin no
StrictModes yes
IgnoreRhosts yes
HostbasedAuthentication no
PermitUserEnvironment no

MaxAuthTries 3
LoginGraceTime 30
MaxStartups 10:30:60
PerSourceMaxStartups 10
PerSourceNetBlockSize 32:128
MaxSessions 4

AllowAgentForwarding no
AllowTcpForwarding no
AllowStreamLocalForwarding no
X11Forwarding no
PermitTunnel no
GatewayPorts no
StreamLocalBindUnlink no

LogLevel VERBOSE
SyslogFacility AUTHPRIV
PrintMotd no
PrintLastLog yes
UseDNS no
FingerprintHash SHA256
ExposeAuthInfo no

ClientAliveInterval 300
ClientAliveCountMax 3
TCPKeepAlive yes
UnusedConnectionTimeout none

KerberosAuthentication no
GSSAPIAuthentication no
GSSAPICleanupCredentials yes

Compression no
```

Файл намеренно не содержит директив, которые либо не дают дополнительного эффекта, либо делают базовый профиль менее переносимым. Например, в нём нет `PerSourcePenalties`, `RefuseConnection`, `ChannelTimeout none`, `RekeyLimit 0 0`, `PermitOpen any` и `PermitListen any`. Причины разобраны ниже.

### Аутентификация

`PubkeyAuthentication yes` явно разрешает публичные ключи. Это основной и единственный разрешённый метод аутентификации в выбранной модели.

`PasswordAuthentication no` отключает парольную SSH-аутентификацию. `KbdInteractiveAuthentication no` отключает интерактивный механизм, через который часто подключают PAM-пароли или одноразовые коды. Отключение только `PasswordAuthentication` недостаточно, если интерактивная аутентификация остаётся доступна.

`PermitEmptyPasswords no` запрещает вход с пустым паролем. При выключенной парольной аутентификации эта директива почти не меняет поведение, но оставляет явный запрет в профиле.

`AuthenticationMethods publickey` фиксирует требование успешно пройти именно публично-ключевую аутентификацию. Это полезно как декларация политики: новые методы, появившиеся в конфигурации из других источников, не должны неожиданно стать альтернативным способом входа.

### Запрет прямого входа под root

`PermitRootLogin no` запрещает SSH-вход непосредственно в учётную запись `root`, в том числе по ключу.

Администрирование должно выполняться через персональную учётную запись с настроенным `sudo`. Такой подход даёт возможность связать действия с конкретным пользователем, отозвать доступ одного администратора без замены общего root-ключа и не использовать суперпользователя для повседневной работы.

До применения этой директивы необходимо проверить, что существует хотя бы одна рабочая административная учётная запись, её публичный ключ установлен, а `sudo` действительно работает.

### Проверка пользовательских файлов и окружения

`StrictModes yes` заставляет `sshd` проверять владельцев и права домашнего каталога пользователя, `.ssh` и файла `authorized_keys`. Это защищает от ситуации, когда посторонний пользователь может изменить список разрешённых ключей.

`IgnoreRhosts yes` и `HostbasedAuthentication no` закрывают старые механизмы доверия между хостами, основанные на `rhosts`/`hosts.equiv` и host-based authentication. В современной модели персонального входа по ключам эти механизмы не нужны.

`PermitUserEnvironment no` запрещает пользователю передавать серверу произвольные переменные окружения через `~/.ssh/environment` и параметры `environment=` в `authorized_keys`. Такие возможности могут влиять на среду запуска процессов и создавать обходы ограничений в специально ограниченных конфигурациях.

### Ограничение попыток и соединений

`MaxAuthTries 3` ограничивает число неудачных попыток аутентификации в рамках одного соединения. Это уменьшает пространство для перебора ключей внутри одной сессии, но может мешать клиенту, который автоматически предлагает серверу множество ключей из агента. На клиенте для таких серверов стоит явно задавать нужный ключ и использовать `IdentitiesOnly yes`.

`LoginGraceTime 30` ограничивает время, в течение которого клиент может оставаться подключённым без успешной аутентификации. Это сокращает срок удержания неаутентифицированных соединений.

`MaxStartups 10:30:60` задаёт глобальную защиту от большого числа одновременных неаутентифицированных соединений. До 10 таких соединений сервер принимает без случайного отказа; после этого вероятность отказа постепенно растёт; при 60 соединениях новые попытки отклоняются. Это не лимит уже вошедших пользователей и не ограничение числа терминалов.

`PerSourceMaxStartups 10` добавляет лимит для одного источника IP-адреса. Он применяется одновременно с глобальным `MaxStartups`, и действует более строгий из двух лимитов. Это полезно, когда большое количество соединений приходит с одного адреса, но требует учитывать NAT и корпоративные VPN: несколько реальных администраторов могут выглядеть для сервера одним источником.

`PerSourceNetBlockSize 32:128` определяет, как группировать адреса при применении per-source ограничений: `/32` для IPv4 и `/128` для IPv6, то есть каждый IP рассматривается отдельно. Это штатные значения по умолчанию, но здесь они записаны явно, чтобы политика была видна в конфигурации. Обе директивы появились в OpenSSH 8.5 и доступны в штатном Debian 12.

`MaxSessions 4` ограничивает количество shell-, login- и subsystem-сессий внутри одного сетевого SSH-соединения. Это важно, например, при использовании мультиплексирования `ControlMaster`. Директива не ограничивает количество независимых TCP-подключений к серверу и не является общим лимитом пользователей.

### Forwarding по умолчанию выключен

Самое важное свойство базового профиля — отсутствие произвольных туннелей:

- `AllowAgentForwarding no` отключает пересылку сокета `ssh-agent` на удалённую сторону.
- `AllowTcpForwarding no` отключает TCP forwarding, включая стандартные варианты `-L`, `-R`, `-D` и используемый `ProxyJump` канал передачи данных.
- `AllowStreamLocalForwarding no` запрещает аналогичное перенаправление Unix-domain sockets.
- `X11Forwarding no` запрещает пересылку X11.
- `PermitTunnel no` запрещает создание туннельных сетевых устройств через SSH.
- `GatewayPorts no` не позволяет удалённым forwarding-listener автоматически становиться доступными на всех сетевых интерфейсах.
- `StreamLocalBindUnlink no` не разрешает удалять существующий Unix socket при создании нового forwarding socket.

Эта политика не означает, что пользователь с полноценным shell-доступом физически не способен построить собственный туннель сторонними программами. Ограничения отключают стандартные механизмы forwarding протокола SSH. Поэтому для учётных записей, которым запрещена интерактивная работа, дополнительно применяются `ForceCommand`, `MaxSessions 0`, `ChrootDirectory` или другие ограничения. Нельзя считать `AllowTcpForwarding no` полноценной песочницей для пользователя, которому оставили обычную оболочку.

В конфиге намеренно отсутствуют `PermitOpen any` и `PermitListen any`. Это разрешительные значения, которые становятся важными после включения forwarding. Пока forwarding выключен, они не дают полезного эффекта. При настройке конкретной роли следует сразу задать ограниченный список целей, а не оставлять явное `any` как напоминание о неограниченном доступе.

`DisableForwarding no` тоже не нужен: значение `no` не добавляет ограничения и не требуется для работы отдельных директив `Allow*`. В ролевых конфигурациях, где нужно запретить абсолютно все виды forwarding, наоборот, полезен `DisableForwarding yes`.

### Логирование

`LogLevel VERBOSE` добавляет полезные для аудита сведения об аутентификации, включая отпечатки использованных ключей. Это более информативный уровень, чем обычный `INFO`, но не настолько подробный, как отладочные уровни `DEBUG`.

`SyslogFacility AUTHPRIV` направляет сообщения в категорию приватных сообщений аутентификации, если это поддерживается и используется системной конфигурацией журналирования. На системах с `systemd-journald` события также можно смотреть через `journalctl`.

`PrintMotd no` отключает дополнительный MOTD (Message of the Day) от `sshd`, а `PrintLastLog yes` сохраняет вывод информации о последнем входе. `FingerprintHash SHA256` фиксирует привычный формат отпечатков ключей SHA-256. `ExposeAuthInfo no` не создаёт для пользовательской сессии дополнительный файл с информацией об использованной аутентификации.

### Keepalive и тайм-ауты

`ClientAliveInterval 300` заставляет сервер отправлять зашифрованный запрос клиенту после пяти минут отсутствия входящих данных. `ClientAliveCountMax 3` разрешает три запроса без ответа. В результате неотвечающий клиент обычно отключается примерно через 15 минут. Это не тайм-аут бездействия пользователя. Живой SSH-клиент отвечает на служебные запросы, даже если человек ничего не печатает. Поэтому интерактивный терминал, открытый на ночь, не обязательно будет закрыт через 15 минут.

`TCPKeepAlive yes` оставляет включённым TCP keepalive на транспортном соединении. Он менее надёжен как индикатор состояния, чем зашифрованные SSH-сообщения `ClientAlive`, но полезен как дополнительный механизм обнаружения оборванного TCP-соединения.

`UnusedConnectionTimeout none` явно сохраняет поведение, при котором аутентифицированное соединение без открытых каналов не закрывается только из-за отсутствия активного канала. Это важно для некоторых сценариев с постоянными forwarding-соединениями.

`ChannelTimeout` в базовый профиль не включён. По умолчанию OpenSSH не закрывает каналы из-за их бездействия. Если позже понадобится закрывать, например, простаивающие TCP-forwarding каналы, следует задать конкретный тип и интервал, например `direct-tcpip=30m`. Значение `ChannelTimeout none` не является корректной заменой отсутствующей директивы: параметр ожидает пары `тип=интервал`.

### Kerberos, GSSAPI и PAM

`KerberosAuthentication no` и `GSSAPIAuthentication no` отключают неиспользуемые механизмы входа через Kerberos и GSSAPI. Если организация использует Active Directory или централизованную Kerberos-аутентификацию, этот раздел нельзя копировать без адаптации.

`GSSAPICleanupCredentials yes` сохраняет безопасное поведение очистки GSSAPI credentials на случай, если GSSAPI будет включён позднее.

В профиле намеренно не задан `UsePAM`. На Debian и RHEL PAM может участвовать в проверках учётной записи и создании пользовательской сессии, даже когда парольная и keyboard-interactive аутентификация отключены. Не следует отключать PAM только ради декларации «вход по ключу»: сначала нужно понимать, какие PAM account/session-модули использует система.

### Сжатие и SFTP

`Compression no` отключает сжатие SSH-трафика. Само по себе сжатие не является универсальной уязвимостью, однако при совместном прохождении доверенных и недоверенных данных по одному соединению оно может создавать условия для утечки информации через побочные каналы. Для административного SSH-соединения обычно нет необходимости включать компрессию ради небольшой экономии трафика.

`Subsystem sftp` намеренно не задаётся в этом drop-in. Штатные пакеты Debian и RHEL обычно уже объявляют подсистему SFTP в основном `/etc/ssh/sshd_config`. Повторное объявление того же имени в файле `.d` приводит к ошибке `Subsystem 'sftp' already defined`, а не переопределяет поставляемую команду. Поэтому системную строку `Subsystem sftp ...` следует оставить на месте. Для ограниченной учётной записи директива `ForceCommand internal-sftp` запускает встроенный SFTP-сервер напрямую и не требует менять глобальное объявление подсистемы.

## Сценарий: дополнительные штрафы по источнику

OpenSSH 9.8 добавил встроенный механизм `PerSourcePenalties`, позволяющий временно отказывать в подключении IP-адресам, демонстрирующим подозрительное поведение. В OpenSSH 10.3 механизм получил дополнительный класс invaliduser, предназначенный для обработки попыток входа с несуществующими именами пользователей.

Механизм штрафов включён по умолчанию, однако стандартные интервалы достаточно короткие. Для публично доступного SSH-сервера имеет смысл установить собственную политику, которая не будет блокировать администратора из-за единичной ошибки, но позволит ограничивать источники при массовых параллельных попытках подключения. Для этого создаём отдельный файл: `/etc/ssh/sshd_config.d/20-ssh-source-penalties.conf`.

```text
PerSourcePenalties crash:10m authfail:15s invaliduser:15s refuseconnection:30s noauth:1s grace-exceeded:30s max:1d min:1m
```

Параметры определяют продолжительность штрафов для различных событий:

| Параметр           | Продолжительность | Назначение                                                              |
| :----------------- | :---------------- | :---------------------------------------------------------------------- |
| `crash`            | `10m`             | Аварийное завершение `sshd`, вызванное источником                       |
| `authfail`         | `15s`             | Завершение соединения после неудачных попыток аутентификации            |
| `invaliduser`      | `15s`             | Попытка входа с несуществующим пользователем                            |
| `refuseconnection` | `30s`             | Отказ подключения через директиву `RefuseConnection`                    |
| `noauth`           | `1s`              | Отключение без попытки аутентификации                                   |
| `grace-exceeded`   | `30s`             | Превышение времени `LoginGraceTime`                                     |
| `max`              | `1d`              | Максимальная продолжительность накопленного штрафа                      |
| `min`              | `1m`              | Минимальный накопленный штраф для применения ограничения                |

Штрафы накапливаются для одного источника, в том числе при одновременных соединениях. Уже установленные соединения принудительно не разрываются, но новые подключения с источника, достигшего порога, отклоняются на соответствующее время. Ограничение не применяется, пока накопленный штраф не достигнет `min`.

Выбранные значения обеспечивают следующий принцип работы:

- Одна ошибка в имени пользователя: штраф `15s`, блокировки нет.
- Одна неудачная аутентификация: штраф `15s`, блокировки нет.
- Несколько одновременных неудачных подключений: штрафы суммируются.
- При достижении накопленного порога `1m` источник временно перестаёт получать возможность подключения.
- При последующих накопленных штрафах продолжительность ограничения может увеличиваться вплоть до `1d`.

`crash:10m` является намеренным исключением: источник, вызвавший аварийное завершение `sshd`, получает ограничение сразу, поскольку его штраф превышает порог `min`. Значение `max` представляет собой верхнюю границу, а не фиксированную продолжительность каждой блокировки. Например, один неудачный вход не приводит к суточному отказу. Для достижения максимального срока необходимо накопить соответствующее количество штрафов. Для `noauth` намеренно оставлено минимальное значение `1s`. Некоторые легитимные инструменты, например `ssh-keyscan`, устанавливают соединение и завершают его без аутентификации. Чрезмерно строгий штраф за такое поведение может затронуть диагностические инструменты и автоматизацию.

Важно отметить, что этот механизм не следует рассматривать как полноценную замену **Fail2ban**. Он встроен непосредственно в `sshd` и оценивает поведение SSH-подключений, а не анализирует произвольные системные журналы. Его задача — автоматически ограничивать подозрительные источники без установки дополнительного программного обеспечения.

У ограничений по адресу есть важная эксплуатационная особенность. OpenSSH учитывает IP-адреса и сетевые диапазоны, определяемые директивой `PerSourceNetBlockSize`. По умолчанию используются 32:128, то есть каждый IPv4- и IPv6-адрес рассматривается отдельно. Однако несколько администраторов за одним NAT, VPN-шлюзом или корпоративным proxy всё равно могут иметь общий внешний IP-адрес и попасть под одну блокировку.

Для исключения доверенных адресов предусмотрена директива `PerSourcePenaltyExemptList`. Её следует использовать только для действительно доверенных и стабильных адресов, избегая широких диапазонов без необходимости.

**Примечание**: выбранные значения являются собственной политикой безопасности, а не стандартными значениями OpenSSH. Отдельный файл нужен для явного документирования и фиксации этой политики. Также важно понимать, что `PerSourcePenalties` особенно полезен против интенсивных параллельных попыток: он не гарантирует блокировку каждого бота, который выполняет редкие последовательные подключения.

## Сценарий: ограничение круга пользователей

Базовый профиль отвечает на вопрос, **как** пользователь может аутентифицироваться. Но он сам по себе не определяет, **кто именно** имеет право входить. Для ограничения списка пользователей применяются `AllowUsers` или `AllowGroups`. Для административного доступа рекомендую создать отдельную группу `ssh-users`. Это позволяет независимо управлять правом SSH-доступа и правом использования `sudo`. На RHEL-подобных системах традиционно встречается группа `wheel`, на Debian — `sudo`, но эти группы обычно предназначены для sudo-политики и не обязательно должны совпадать с группой SSH-доступа.

Создайте отдельную системную группу, если группа уже существует, повторно создавать её не нужно.

```bash
sudo groupadd --system ssh-users
```

Затем добавьте в группу всех пользователей, которым необходим SSH-доступ:

```bash
sudo usermod -aG ssh-users admin
sudo usermod -aG ssh-users deploy
```

И наконец, создайте файл `/etc/ssh/sshd_config.d/30-allow-users.conf`:

```text
AllowGroups ssh-users
```

После этого каждый пользователь, которому нужен SSH-доступ, должен входить в эту группу.

**ВАЖНО**: не включайте ограничение, пока не проверили все интерактивные и сервисные учётные записи. Если CI, Ansible, backup или мониторинг подключаются по SSH, они тоже должны попасть в разрешённый список. `AllowUsers` и `AllowGroups` — это глобальные фильтры входа, поэтому ошибка в них может отрезать доступ не только администратору, но и автоматизации.

Также не стоит добавлять бессмысленные запреты вроде `DenyUsers nobody` ради видимости строгой политики. Системная учётная запись без корректной оболочки и с заблокированным паролем не должна становиться разрешённым пользователем только потому, что её имя отсутствует в `DenyUsers`.

## Сценарий: сервер как Jump Host / bastion

У Jump Host появляется конкретная задача: принять SSH-подключение администратора и передать его TCP-соединение к заранее разрешённому внутреннему серверу. Сам bastion не должен автоматически получать доступ к приватному ключу администратора или выступать полноценным рабочим местом.

Для `ProxyJump` требуется разрешить клиентское TCP-forwarding. Это именно `AllowTcpForwarding local`: клиент просит jump-сервер открыть соединение к целевому адресу. Сначала создаётся отдельная группа:

```bash
sudo groupadd ssh-jump
sudo usermod -aG ssh-jump bastion-user
```

Затем создаётся файл `/etc/ssh/sshd_config.d/40-ssh-role-jump.conf`:

```text
Match Group ssh-jump
    AllowTcpForwarding local
    AllowStreamLocalForwarding no
    AllowAgentForwarding no
    X11Forwarding no
    PermitTunnel no
    GatewayPorts no
    PermitOpen 10.20.0.10:22 10.20.0.11:22
    MaxSessions 0
Match all
```

Адреса в `PermitOpen` нужно заменить на реальные внутренние цели. Разрешается только соединение к перечисленным парам `host:port`. Если сервер должен давать доступ к нескольким внутренним SSH-хостам, каждый из них добавляется явно. Имя хоста в списке должно соответствовать имени, которое SSH-клиент передаёт в запросе forwarding; при использовании DNS нужно учитывать, где именно разрешается это имя.

`MaxSessions 0` — особенно полезное ограничение для jump-учётной записи. Оно запрещает shell-, login- и subsystem-сессии, но оставляет forwarding. Следовательно, пользователь может использовать bastion как транспортный узел, но не может открыть на нём обычный терминал или SFTP-сессию.

`AllowAgentForwarding no` оставлен намеренно. Для стандартного `ProxyJump` передавать агент на bastion не требуется: клиент устанавливает сквозное SSH-соединение с целевым сервером через канал forwarding. Ключ для входа на целевой сервер остаётся на клиентской стороне. На клиенте можно описать bastion так:

```text
Host bastion
    HostName bastion.example.net
    User bastion-user
    IdentityFile ~/.ssh/id_ed25519_bastion
    IdentitiesOnly yes

Host private-*
    ProxyJump bastion
```

После этого подключение к внутреннему узлу выполняется обычной командой:

```bash
ssh admin@private-server
```

Либо без клиентского alias:

```bash
ssh -J bastion-user@bastion.example.net admin@10.20.0.10
```

У такого bastion остаётся важная внешняя зависимость: он должен иметь сетевой маршрут к разрешённым целям, а firewall должен допускать соединения к ним. `PermitOpen` не создаёт маршрут и не заменяет сетевую фильтрацию; он лишь ограничивает цели, которые `sshd` разрешает открыть через TCP-forwarding.

## Сценарий: доступ к code-server через SSH-туннель

Удалённая IDE — хороший пример того, почему forwarding не следует включать глобально. Серверу может понадобиться один конкретный TCP-туннель до локального `code-server`, но это не означает, что всем SSH-пользователям нужно разрешать `-L`, `-R` и динамический SOCKS. Рекомендуемая схема состоит из трёх частей:

1. `code-server` слушает только loopback-интерфейс удалённой машины.
2. SSH разрешает локальный TCP-forwarding только выделенной группе.
3. `PermitOpen` разрешает подключение только к `127.0.0.1:8080`.

Создайте группу и добавьте в неё пользователя, которому нужен доступ:

```bash
sudo groupadd ssh-code-server
sudo usermod -aG ssh-code-server rune
```

Добавьте `/etc/ssh/sshd_config.d/41-ssh-role-code-server.conf`:

```text
Match Group ssh-code-server
    AllowTcpForwarding local
    PermitOpen 127.0.0.1:8080
    AllowStreamLocalForwarding no
    AllowAgentForwarding no
    X11Forwarding no
    PermitTunnel no
    GatewayPorts no
Match all
```

На сервере `code-server` должен слушать адрес `127.0.0.1`, а не `0.0.0.0`. Для типовой установки соответствующие параметры в `~/.config/code-server/config.yaml` выглядят так:

```yaml
bind-addr: 127.0.0.1:8080
auth: password
cert: false
```

Парольную аутентификацию самого `code-server` можно оставить включённой как дополнительный уровень защиты. Если её отключают и полагаются только на SSH-аутентификацию, нужно особенно внимательно ограничить группу SSH-доступа и убедиться, что локальный порт не опубликован на внешнем интерфейсе.

На клиентской машине запускается:

```bash
ssh -N -L 8080:127.0.0.1:8080 rune@server.example.net
```

После установления соединения браузер открывает:

```text
http://127.0.0.1:8080
```

Первый `127.0.0.1:8080` — локальный адрес на компьютере администратора. Второй — адрес и порт, к которым SSH-сервер подключается со своей стороны. Поэтому `PermitOpen 127.0.0.1:8080` ограничивает серверную цель, а не локальный порт на компьютере пользователя. Здесь не требуется `GatewayPorts yes`, поскольку мы не создаём удалённый listener. Не требуется и `AllowTcpForwarding yes`: разрешение `local` уже достаточно для `ssh -L`. Не следует открывать порт `8080` во внешнем firewall, если доступ должен идти исключительно через SSH-туннель.

Если сервис переедет на другой порт, например `127.0.0.1:3000`, нужно согласованно изменить и `PermitOpen`, и команду `ssh -L`. Если будет использоваться Unix socket, это уже другой механизм: потребуется отдельно продумать `AllowStreamLocalForwarding` и ограничения для соответствующего socket path.

## Сценарий: SFTP-only пользователь

Иногда пользователю нужен не shell, а только загрузка и выгрузка файлов. В этом случае недостаточно отключить TCP-forwarding: обычная учётная запись всё ещё может получить shell. Следует принудительно запускать внутренний SFTP-сервер и ограничить файловое пространство через `chroot`. Сначала создаётся отдельная группа:

```bash
sudo groupadd sftp-only
sudo usermod -aG sftp-only file-user
```

Затем в `/etc/ssh/sshd_config.d/50-ssh-role-sftp-only.conf` добавляется:

```text
Match Group sftp-only
    ChrootDirectory /srv/sftp/%u
    ForceCommand internal-sftp
    DisableForwarding yes
    PermitTTY no
    X11Forwarding no
Match all
```

Для пользователя `file-user` структура каталогов может выглядеть так:

```text
/srv/sftp/file-user/          root:root       0755
/srv/sftp/file-user/upload/   file-user:...   0750
```

Каталог, указанный в `ChrootDirectory`, и все компоненты пути к нему должны принадлежать `root` и не быть доступны для записи группе или остальным пользователям. Поэтому пользователь не может владеть корнем своего chroot-каталога. Для загрузки файлов ему выделяется отдельный подкаталог, например `upload`, которым пользователь уже владеет.

Домашний каталог пользователя должен соответствовать каталогу внутри `chroot`, например `/upload`, а не внешнему пути `/srv/sftp/file-user/upload`. При необходимости это задаётся отдельно в учётной записи пользователя. Перед вводом в эксплуатацию нужно проверить права каждого компонента пути, а не только конечного каталога.

`ForceCommand internal-sftp` принудительно запускает SFTP независимо от команды, которую клиент пытается передать. Но сам по себе `ForceCommand` не запрещает forwarding. Поэтому в блоке дополнительно используется `DisableForwarding yes`. `PermitTTY no` запрещает выделение интерактивного терминала.

Важное отличие от Jump Host: здесь нельзя задавать `MaxSessions 0`, поскольку SFTP является subsystem-сессией. Значение `0` запретило бы и сам файловый доступ.

## Применение конфигурации

Изменение SSH-конфигурации удалённого сервера всегда следует выполнять с сохранённым действующим сеансом. До проверки нового подключения не закрывайте текущую административную сессию. Для облачной машины дополнительно убедитесь, что доступна консоль провайдера или другой независимый способ восстановления.

Сначала сохраните копию каталога:

```bash
sudo cp -a /etc/ssh/sshd_config.d "/etc/ssh/sshd_config.d.backup.$(date +%F-%H%M%S)"
```

После создания или изменения файла проверьте владельца и права:

```bash
sudo chown root:root /etc/ssh/sshd_config.d/00-ssh-hardening.conf
sudo chmod 0600 /etc/ssh/sshd_config.d/00-ssh-hardening.conf
```

Если добавлялись ролевые файлы, права нужно проверить и для них. Затем обязательно выполните синтаксическую проверку:

```bash
sudo sshd -t
```

Отсутствие вывода и код возврата `0` означают, что конфигурация прошла синтаксическую проверку. Это ещё не доказывает, что для каждого пользователя получилась именно та политика, которую ожидал администратор.

Для проверки итоговых глобальных значений используйте:

```bash
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods|permitrootlogin|allowtcpforwarding|allowagentforwarding|allowstreamlocalforwarding|maxauthtries|maxstartups|maxsessions|loglevel|compression) '
```

Для проверки конкретного пользователя и источника можно вычислить конфигурацию с учётом `Match`:

```bash
sudo sshd -T -C user=rune,host=client.example.net,addr=192.0.2.25 | grep -E '^(allowtcpforwarding|permitopen|allowagentforwarding|maxsessions|forcecommand|chrootdirectory) '
```

В примере нужно заменить пользователя, имя клиента и адрес источника на реальные значения. Для Jump Host и `code-server` эта проверка особенно важна: нужно убедиться, что нужная группа получает forwarding, а обычный пользователь по-прежнему его не получает. Только после успешной проверки конфигурацию можно перечитать службой.

Затем откройте **новое независимое SSH-подключение** и проверьте вход. Если включался Jump Host, проверьте `ssh -J`. Если настраивался `code-server`, проверьте локальный туннель и доступ к веб-интерфейсу. Если добавлялся SFTP-only пользователь, проверьте, что SFTP работает, а shell и forwarding не предоставляются.

Если новый вход не работает, не закрывайте старый сеанс. Верните предыдущий файл или удалите только что добавленный ролевой фрагмент, снова выполните `sshd -t` и перечитайте службу. Именно поэтому изменения SSH лучше вносить небольшими независимыми файлами, а не одним большим конфигом с десятками не связанных между собой исключений.

## Организация SSH-клиента

Клиентскую конфигурацию SSH рекомендуется организовать по тому же принципу, что и серверную: основной конфигурационный файл должен оставаться минимальным, а настройки отдельных серверов и окружений следует хранить в самостоятельных файлах. Для этого создаём каталог `~/.ssh/config.d/`, а в основном файле `~/.ssh/config` оставляем только директиву подключения дополнительных конфигураций:

```text
Include ~/.ssh/config.d/*.conf
```

Создаём каталог и устанавливаем необходимые права доступа:

```bash
mkdir -p ~/.ssh/config.d

chmod 700 ~/.ssh
chmod 700 ~/.ssh/config.d

touch ~/.ssh/config
chmod 600 ~/.ssh/config

chmod 600 ~/.ssh/config.d/*.conf
```

Для каждого сервера или группы серверов создаётся отдельный конфигурационный файл. Например, `~/.ssh/config.d/10-production.conf`:

```text
Host production
    HostName 192.168.1.100
    Port 2222
    User admin
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
```

После этого подключение выполняется по короткому псевдониму: `ssh production`. Вместо ручного указания адреса, порта, имени пользователя и ключа достаточно использовать имя, определённое в директиве `Host`. Это уменьшает вероятность ошибки при подключении и позволяет не запоминать параметры каждого сервера.

Конфигурацию также удобно разделять по назначению:

```text
~/.ssh/
├── config
└── config.d/
    ├── 10-production.conf
    ├── 20-homelab.conf
    ├── 30-jump-hosts.conf
    └── 90-defaults.conf
```

При организации файлов необходимо учитывать порядок их обработки. OpenSSH раскрывает маску `Include` в лексикографическом порядке, а для большинства параметров использует первое найденное значение. Поэтому индивидуальные настройки серверов следует размещать раньше общих правил `Host *`. В противном случае общие параметры могут оказаться приоритетнее индивидуальных.

### Использование SSH-агента

При использовании закрытых SSH-ключей, защищённых парольной фразой (passphrase), рекомендуется загружать их в `ssh-agent` перед началом работы. Это позволяет разблокировать ключ один раз и использовать его для последующих подключений без повторного ввода парольной фразы. Например, для загрузки ключа на восемь часов:

```bash
ssh-add -t 8h ~/.ssh/id_ed25519
```

SSH-агент хранит доступ к уже разблокированным ключам и выполняет операции подписи по запросу SSH-клиента. Сам закрытый ключ при этом не передаётся серверу.

Использование агента особенно удобно при работе с несколькими серверами и несколькими ключами. Однако следует помнить, что парольная фраза защищает ключ локально: её неправильный ввод не является ошибкой аутентификации на удалённом сервере. Проблемы возникают уже тогда, когда клиент устанавливает соединение, но не может предъявить подходящий ключ.

### Проверка клиентской конфигурации

Перед подключением к новому серверу полезно проверить, какие параметры SSH-клиент фактически применит:

```bash
ssh -G production | grep -E '^(hostname|user|port|identityfile|identitiesonly) '
```

Команда `ssh -G` выводит результирующую конфигурацию для указанного псевдонима без установки сетевого соединения. Это позволяет заранее обнаружить ошибочный адрес, порт, имя пользователя или путь к ключу. Для диагностики непосредственно процесса подключения можно использовать подробный режим:

```bash
ssh -v production
```

Он показывает этапы установления соединения, выбор ключей и процесс аутентификации. Таким образом, рекомендуется придерживаться нескольких простых правил: хранить настройки серверов раздельно, использовать псевдонимы вместо ручного набора параметров, загружать необходимые закрытые ключи в SSH-агент и проверять результирующую конфигурацию перед подключением. Такая организация делает SSH-клиент предсказуемым в повседневной работе, упрощает сопровождение большого количества серверов и снижает вероятность ошибок при ручном подключении.
